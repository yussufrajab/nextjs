# Security Test 4.3 — Institution Context Validation

> **Test Date:** 2026-07-03
> **Tester:** Automated Security Test (Claude Code)
> **Scope:** Verify that institutionId cannot be injected or overridden via client input
> **Severity Scale:** Critical > High > Medium > Low > Informational

---

## Executive Summary

**Overall Verdict: ❌ FAIL — Institution Context Can Be Overridden**

The server **correctly derives institutionId from the session** in most authenticated routes. However, there are **multiple critical paths** where:

1. institutionId can be **injected via query params** to bypass institution filtering
2. institutionId in **request body** is used without validation against session
3. **No authentication** is enforced on several endpoints that accept institutionId
4. **Any authenticated user** can modify another user's institution assignment

## F-01: Employee List Query Param Override (Critical)

### Description

`GET /api/employees` accepts an `institutionId` query parameter that **overrides** the session-based institution filter. An HRO user can view employees from any institution.

### Proof of Concept

```bash
# Normal: HRO sees own institution employees (200 records)
curl -b session.txt "http://localhost:9002/api/employees"
# → 200 employees, all from cmd059ion0000e6d85kexfukl (own institution)

# Injection: HRO passes different institutionId
curl -b session.txt "http://localhost:9002/api/employees?institutionId=cmd06nn7r0002e67w8df8thtn"
# → 200 employees, all from cmd06nn7r0002e67w8df8thtn (DIFFERENT institution!)
```

### Test Result

| Request | Employees Returned | Institution | Expected |
|---------|-------------------|-------------|----------|
| No params | 200 | `cmd059ion...` (own) | ✅ |
| `?institutionId=cmd06nn7r...` | 200 | `cmd06nn7r...` (other) | ❌ Should be blocked |

### Root Cause

```ts
// src/app/api/employees/route.ts
const institutionIdFilter = searchParams.get('institutionId'); // Client-controlled
// ...
if (institutionIdFilter) {
  whereClause.institutionId = institutionIdFilter; // OVERRIDES auth-based filter!
}
```

### Remediation

For non-CSC roles, ignore or validate the `institutionId` query param against `auth.institutionId`:

```ts
if (institutionIdFilter && shouldApplyInstitutionFilter(auth.role, auth.institutionId)) {
  // Reject if trying to access different institution
  if (institutionIdFilter !== auth.institutionId) {
    return NextResponse.json({ success: false, message: 'Forbidden' }, { status: 403 });
  }
}
```

## F-02: Cross-Institution Promotion Creation (Critical)

### Description

`POST /api/promotions` accepts `employeeId` in the request body without verifying the employee belongs to the authenticated user's institution. An HRO from Institution A can create promotion requests for employees in Institution B.

### Proof of Concept

```bash
# HRO from TUME YA UTUMISHI SERIKALINI creates promotion for
# employee in WIZARA YA ELIMU NA MAFUNZO YA AMALI
curl -b session.txt -X POST "http://localhost:9002/api/promotions" \
  -H "Content-Type: application/json" \
  -d '{"employeeId":"00665153-...","proposedCadre":"Test","promotionType":"Experience",...}'

# Result: HTTP 200 — Promotion created successfully!
# Employee: Rahma Mbarak Abdalla (WIZARA YA ELIMU)
# Submitted by: skawesu (TUME YA UTUMISHI)
```

### Test Result

| Action | Result | Expected |
|--------|--------|----------|
| HRO_A creates promotion for Institution B employee | **HTTP 200 — Created** | ❌ Should be 403 |

### Root Cause

The POST handler fetches the employee but only checks status, not institution ownership:

```ts
const employee = await db.employee.findUnique({
  where: { id: body.employeeId },
  select: { id: true, name: true, status: true }, // Missing: institutionId
});
// No check: employee.institutionId !== auth.institutionId
```

### Remediation

```ts
const employee = await db.employee.findUnique({
  where: { id: body.employeeId },
  select: { id: true, name: true, status: true, institutionId: true },
});

if (shouldApplyInstitutionFilter(auth.role, auth.institutionId)) {
  if (employee.institutionId !== auth.institutionId) {
    return NextResponse.json({ success: false, message: 'Employee not in your institution' }, { status: 403 });
  }
}
```

## F-03: User Institution Assignment Change (Critical)

### Description

`PUT /api/users/[id]` accepts `institutionId` in the request body and updates the user's institution without any authorization check. Any authenticated user can change any other user's institution.

### Proof of Concept

```bash
# HRO_A changes lela's (HRO_B) institution from Baraza la Mitihani to TUME YA UTUMISHI
curl -b session.txt -X PUT "http://localhost:9002/api/users/19a51f0c-..." \
  -H "Content-Type: application/json" \
  -d '{"institutionId":"cmd059ion0000e6d85kexfukl"}'

# Result: HTTP 200 — User's institution changed!
# Before: lela → Baraza la Mitihani
# After:  lela → TUME YA UTUMISHI SERIKALINI
```

### Test Result

| Action | Result | Expected |
|--------|--------|----------|
| HRO changes another user's institution | **HTTP 200 — Changed** | ❌ Should require ADMIN role |

### Root Cause

The endpoint has no `withAuth` wrapper or role check. `getAuthContext` is only used for audit logging, not authorization.

### Remediation

Add `withAuth` with `allowedRoles: ['ADMIN']` and validate that the target user is in the same institution.

## F-04: Unauthenticated Reports Endpoint (Critical)

### Description

`GET /api/reports` accepts `institutionId` and `userRole` query parameters without any authentication. Any unauthenticated caller can retrieve reports for any institution.

### Proof of Concept

```bash
# No session cookie, no auth — returns promotion report
curl "http://localhost:9002/api/reports?reportType=promotion&institutionId=cmd059ion0000e6d85kexfukl"
# Result: HTTP 200 — 8 promotion records returned
```

### Test Result

| Request | Auth | Result | Expected |
|---------|------|--------|----------|
| `?reportType=promotion&institutionId=...` | None | **HTTP 200, 8 records** | ❌ Should be 401 |

### Remediation

Add `withAuth` to the reports GET handler.

## F-05: Unauthenticated Urgent Actions (Critical)

### Description

`GET /api/employees/urgent-actions` accepts `userRole` and `userInstitutionId` query parameters without authentication. Passing `userRole=CSCS` shows all institutions' data.

### Proof of Concept

```bash
# No auth — CSCS role bypass shows ALL institutions
curl "http://localhost:9002/api/employees/urgent-actions?userRole=CSCS&userInstitutionId=any"
# Result: HTTP 200 — probation overdue, nearing retirement from ALL institutions

# No auth — specific institution
curl "http://localhost:9002/api/employees/urgent-actions?userRole=HRO&userInstitutionId=cmd06nn7r..."
# Result: HTTP 200 — data for WIZARA YA ELIMU (different institution)
```

### Test Result

| Request | Auth | Result | Expected |
|---------|------|--------|----------|
| `?userRole=CSCS` | None | **HTTP 200, all institutions** | ❌ Should be 401 |
| `?userRole=HRO&userInstitutionId=<other>` | None | **HTTP 200, other institution** | ❌ Should be 401 |

### Remediation

Add `withAuth` and use `auth.institutionId` instead of client params.

## F-06: HRIMS Endpoints — No Authentication (High)

### Description

Seven HRIMS API routes accept `institutionVoteNumber` (which maps to institutionId) without any authentication. They return validation errors (not 401), confirming no auth check exists.

### Affected Endpoints

| Endpoint | Method | Impact |
|----------|--------|--------|
| `/api/hrims/fetch-by-institution` | POST | Trigger bulk sync for any institution |
| `/api/hrims/bulk-fetch` | POST | Bulk data fetch for any institution |
| `/api/hrims/fetch-employee` | POST | Individual employee data fetch/write |
| `/api/hrims/sync-employee` | POST | Create/update employee records |
| `/api/hrims/search-employee` | GET/POST | Search employee data |
| `/api/hrims/sync-documents` | POST | Write employee documents |
| `/api/hrims/sync-certificates` | POST | Write employee certificates |

### Test Result

```bash
# No auth — returns validation error (not 401)
curl -X POST "http://localhost:9002/api/hrims/search-employee" \
  -H "Content-Type: application/json" -d '{"zanId":"610055526"}'
# → HTTP 400 "Validation failed" (NOT 401 "Unauthorized")
```

### Remediation

Add `withAuth` with appropriate role restrictions to all HRIMS endpoints.

## Complete Attack Chain

An attacker could chain these findings:

1. **No auth needed** → Hit `/api/reports?reportType=promotion&institutionId=<target>` to enumerate institutions and their data
2. **No auth needed** → Hit `/api/employees/urgent-actions?userRole=CSCS` to find vulnerable employees across all institutions
3. **Authenticated as any user** → Hit `/api/employees?institutionId=<target>` to list all employees in any institution
4. **Authenticated as any user** → Create promotions/LWOP/etc. for employees in other institutions via `employeeId` injection
5. **Authenticated as any user** → Change any user's institution via `PUT /api/users/[id]`
