# Security Test 4.1 — Institution-Based Access Control

> **Test Date:** 2026-07-03
> **Tester:** Automated Security Test (Claude Code)
> **Scope:** Institution isolation for HRO role users across API endpoints
> **Severity Scale:** Critical > High > Medium > Low > Informational

---

## Executive Summary

**Overall Verdict: ❌ FAIL — Multiple Critical Vulnerabilities Found**

Institution-based access control is **partially implemented** on list endpoints but has **critical gaps** on individual resource endpoints and **completely broken authentication** on three routes. An attacker can:

1. **Access all LWOP, Retirement, and Service Extension data without any authentication** (Critical)
2. **Escalate privileges** from HRO to CSCS via client-supplied query parameters (Critical)
3. **Modify any request from any institution** via IDOR on `[id]` PATCH endpoints (High)

## F-01: Unauthenticated Data Access (Critical)

### Description

Three API routes return sensitive employee request data **without any authentication**. The `GET` handlers do not call `verifyAuth()` and trust client-supplied `userRole` and `userInstitutionId` query parameters.

### Affected Endpoints

| Endpoint | Records Exposed | Data Type |
|----------|----------------|-----------|
| `GET /api/lwop-requests` | 63 | Leave Without Pay requests |
| `GET /api/retirement-requests` | 43 | Retirement requests |
| `GET /api/service-extension-requests` | 21 | Service extension requests |

### Proof of Concept

```bash
# No cookies, no auth — returns ALL LWOP requests
curl "http://localhost:9002/api/lwop-requests?userRole=CSCS&userInstitutionId=any"

# Result: 63 records with employee names, reasons, documents, etc.
```

**Unauthenticated response (HTTP 200):**
```json
[
  {
    "id": "5723ae09-85c3-4adc-8ac1-20bc6d21a72c",
    "status": "Approved",
    "duration": "13 months",
    "reason": "KUFANYA KAZI SHIRIKA LA ILO",
    "documents": ["lwop/letters/..."],
    "employeeId": "...",
    ...
  }
]
```

### Root Cause

These routes read `userRole` and `userInstitutionId` from `searchParams` (client-controlled) instead of from `verifyAuth()`:

```ts
// VULNERABLE CODE (e.g., lwop-requests/route.ts)
const userRole = searchParams.get('userRole');
const userInstitutionId = searchParams.get('userInstitutionId');
// No verifyAuth() call — trusts client completely
```

### Impact

- **Confidentiality:** Any internet user can read all LWOP, retirement, and service extension requests
- **Data exposed:** Employee names, reasons for leave, medical information, document URLs, dates
- **Compliance:** Violates data protection requirements for government HR systems

### Remediation

Replace client-supplied params with server-side auth:

```ts
// FIX: Use verifyAuth() for all GET handlers
const authResult = await verifyAuth(req);
if (!authResult.authenticated) {
  return authResult.response!;
}
const { role, institutionId } = authResult.context!;
```

## F-02: Privilege Escalation via Client-Supplied Role (Critical)

### Description

The same three routes (`lwop-requests`, `retirement-requests`, `service-extension-requests`) allow any authenticated user to pass `userRole=CSCS` as a query parameter, bypassing institution filtering and gaining access to **all data across all institutions**.

### Proof of Concept

```bash
# HRO user passes userRole=CSCS to see ALL institutions' data
curl -b session_cookies.txt \
  "http://localhost:9002/api/lwop-requests?userRole=CSCS&userInstitutionId=cmd059ion0000e6d85kexfukl"

# Result: 63 records from ALL institutions (not just the HRO's own)
```

### Impact

- An HRO from any institution can view **all** LWOP, retirement, and service extension data across the entire government
- Combined with F-01, this works **without authentication**

### Remediation

Same as F-01 — never trust client-supplied role/institution parameters.

## F-03: IDOR on `[id]` PATCH Endpoints (High)

### Description

All individual request resource endpoints (`/api/{type}/[id]`) allow any authenticated user to modify requests from **any institution**. The endpoints verify authentication but do NOT check that the resource belongs to the user's institution.

### Affected Endpoints

| Endpoint | HTTP Methods | Vulnerable |
|----------|-------------|------------|
| `/api/promotions/[id]` | PATCH, PUT | ❌ Yes |
| `/api/confirmations/[id]` | PATCH, PUT | ❌ Yes |
| `/api/lwop/[id]` | PATCH, PUT | ❌ Yes |
| `/api/cadre-change/[id]` | PATCH, PUT | ❌ Yes |
| `/api/resignation/[id]` | PATCH, PUT | ❌ Yes |
| `/api/retirement/[id]` | PATCH, PUT | ❌ Yes |

### Proof of Concept

```bash
# HRO_B (Institution B) modifies Institution A's promotion request
curl -b hro_b_cookies.txt \
  -X PATCH "http://localhost:9002/api/promotions/{institution_a_request_id}" \
  -H "Content-Type: application/json" \
  -d '{"status":"MaliciousStatus","reviewStage":"HRO Review"}'

# Result: HTTP 200 — request modified successfully
```

### Test Results

| Request Type | Cross-Institution PATCH | Result |
|-------------|------------------------|--------|
| Promotion | HRO_B → Institution A request | **HTTP 200 — Modified** |
| Confirmation | HRO_B → Institution A request | **HTTP 200 — Modified** |
| LWOP | HRO_B → Institution A request | **HTTP 200 — Modified** |
| Cadre Change | HRO_B → Institution A request | **HTTP 200 — Modified** |
| Resignation | HRO_B → Institution A request | **HTTP 200 — Modified** |
| Retirement | HRO_B → Institution A request | **HTTP 200 — Modified** |

### Root Cause

The `[id]` routes fetch the request by ID without checking institution ownership:

```ts
// VULNERABLE: No institution check after fetching
const existingRequest = await db.promotionRequest.findUnique({
  where: { id },
  include: { Employee: true },
});
// Missing: if (existingRequest.Employee.institutionId !== auth.institutionId) return 403
```

### Impact

- Any HRO/HRMO/HHRMD can **approve, reject, or modify** requests from any other institution
- Could lead to unauthorized approval of promotions, retirements, or separations
- Audit trail would show the wrong reviewer

### Remediation

Add institution ownership check after fetching the resource:

```ts
const existingRequest = await db.promotionRequest.findUnique({
  where: { id },
  include: { Employee: true },
});

if (!existingRequest) {
  return new NextResponse('Not found', { status: 404 });
}

// ADD: Institution ownership check
if (shouldApplyInstitutionFilter(auth.role, auth.institutionId)) {
  if (existingRequest.Employee.institutionId !== auth.institutionId) {
    return new NextResponse('Forbidden', { status: 403 });
  }
}
```
